Canonical authored guide

Human and agent onboarding

Use the same operating truth while preserving one writer for every record type.

Ownership boundary

Project OS

Tasks, sprints, runs, packets, memory, docs routes, UI campaigns, schemas, checks, and projections.

Agent Base

Shared skills, lane/model routing, spawning, supervision, messaging, telemetry, and persistent panes.

Project-local adapters

Product commands, browser/generation helpers, tracker bridges, deployment checks, security policy, and domain skills.

No owner may create a second backlog or hidden approval store.

Agent cold pickup

  1. Read root and nearest AGENTS.md.
  2. Read PROJECT-OS.html.
  3. Run project-os onboard --json; stop on integrity errors.
  4. Select an unblocked canonical task.json and its linked run packet; read events, evidence, sprint, and run state.
  5. Consult repo facts, edit maps, current docs, decisions, proof, prior runs, research dead ends, and memory.
  6. Choose a declared capability route. Use Agent Base for live execution and project-local adapters at the product edge.
  7. State back outcome, task, write fence, dependencies, human gates, verification, and return destination.
  8. Verify, classify durable outputs, rebuild, check, and hand off from repository evidence.

Human pickup

Open .project-os/generated/onboarding.html. Address explicit human gates, blockers, and UI review first. Record judgments in the owning task or decision record, then rebuild; never edit generated HTML.

Greenfield adoption

  1. Initialize with project name, timeless summary, and desired outcome.
  2. Inspect the generated cockpit and JSON health report.
  3. Verify and promote REPO-FACTS.html and EDIT-MAPS.html.
  4. Declare capability routes without copying shared runtime skills.
  5. Create one outcome-shaped task; add sprint/run coordination only when needed.

Existing-repository migration

  1. Inventory rules, task authority, docs, capabilities, generated paths, verification, UI artifacts, trackers, and archive policy without mutation.
  2. Choose one writer per concern and use one-way adapters for retained external authorities.
  3. Merge the staged agent rules deliberately.
  4. Classify knowledge through reviewed move manifests; adopt active work before bulk history.
  5. Inventory project capabilities and route shared runtime behavior to Agent Base.
  6. Model only active UI decisions; retain old galleries as evidence or archive.
  7. Build, inspect, check, and cut over one canonical route at a time.

Unresolved collisions stop that boundary without damaging the existing repository.

UI decision and proof

A complete campaign has a bounded candidate manifest, deterministic review projection, imported response, exhaustive decision, chosen-direction implementation, same-commit verification, and a task-evidence fold resolved by task ID plus stable evidence filename. Campaign verification never closes the task.

Handoff gate

  1. Update canonical task/run records.
  2. Attach commands, revision, and observed evidence.
  3. Classify decisions, docs, memory, task evidence, and raw history.
  4. Run project-os build and read-only project-os check --json.
  5. Report PASS, FAIL, BLOCKED, or not-observed with the next canonical record.

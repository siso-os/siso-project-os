SISO Project Kit specification

Status: implementation contract · Profile: complete-siso-project-kit · Date: 2026-07-29

Install the reusable operating patterns proven in a large live agent-operated project without importing its product facts, customer evidence, runtime credentials, machine paths, or historical state.

Boundaries

  • Project OS owns project-local records, schemas, HTML authorities, projections, migrations, and integrity gates.
  • The optional Fleet Runtime Pack owns project-local programme/domain/repository/policy contracts, admission receipts, callbacks, and read-only fleet projections.
  • Codex CLI, Claude Code, or another compatible agent CLI executes the core lifecycle directly.
  • Optional providers may own spawning, model routing, messaging, telemetry, and persistent terminal/pane control; the Fleet Pack does not duplicate them.
  • Applications own product code, credentials, deployment policy, endpoints, and project-specific adapters.
  • Checks diagnose and fail closed; they never repair authored state implicitly.

Hard invariants

  1. One canonical task ID; sprints, runs, UI campaigns, fleet admission, and external trackers reference it.
  2. Folder state and record state agree; terminal task records are immutable.
  3. Mission ownership, registries, write claims, sprints, runs, fleet admission receipts, and delivery mutations use exclusive locks or atomic directory replacement.
  4. Write fences contain concrete repository-relative paths and cannot overlap without explicit sequencing.
  5. Dispatched packets are immutable and digest-pinned; amendments name their predecessor.
  6. A worker claim is never verification. Passed verification requires distinct actor and verifier identities and an in-fence changed-file verdict.
  7. Fleet eligibility, provider process start, completion, and qualification are separate states; none implies another.
  8. A writer is never eligible without an exact active claim; the provider must atomically revalidate canonical claims, live assignments, verifier backlog, and machine thresholds while reserving the process slot.
  9. Landed work names one candidate SHA and proves remote equality when push is authorized.
  10. Generated HTML/JSON is deterministic and never canonical.
  11. Optional runtime-provider capabilities are dependencies, never copied project authorities.
  12. Existing-repository and fleet-pack adoption preserves every collision and reports unresolved authorities.

Format and discovery

JSON/JSONL is canonical machine state. Deterministic HTML with embedded JSON is the substantive human/agent interface. Engine-required Markdown files contain only discovery and routing. Nearest AGENTS.md rules win; the root router points to the project operator shim and HTML authority.

Release acceptance

  1. Greenfield init passes architecture, capability, lifecycle, knowledge, UI, and deterministic build checks.
  2. Existing-repository adoption preserves source bytes, reports collisions and legacy Markdown, merges only runtime pointers, and emits HTML+JSON migration evidence.
  3. All schemas self-validate and all canonical artifact families are traversed by read-only check.
  4. Optional Fleet Pack plan/init/check is collision-safe, crash-resumable, and idempotent; collision, case-folded collision, reserved-control-path scope, blocked DAG, verifier backlog, stale heartbeat, disk pressure, dirty worktree, missing or redirected Git/evidence facts, non-file evidence, task/domain mismatch, claim/capacity bypass, verifier-lineage spoof, profile or process-plan swap, invalid installed version, managed-artifact or receipt mutation, malformed policy, secret, and ownership-overlap fixtures fail closed.
  5. Admission receipts are lock-protected, write-once, and digest-bearing; their digest provides mutation detection, not signer identity or provider capacity.
  6. The public-safe Actionist dog-food rehearsal admits an independent verifier, claim-binds and holds an unsafe conversion, passes both checks, and mutates no live programme state.
  7. Strict UI campaigns account for every direction/candidate, import raw human review, link exact implementation and verification commits, and fold proof into the canonical task.
  8. Package inventory contains only runtime, templates, HTML docs, schemas, tests/scripts, examples, and license.
  9. No protected source paths, private product facts, customer data, credentials, or private source-project identifiers enter the package; explicitly sanitized dog-food fixture names are permitted.
  10. GitHub package install succeeds from the released tag.

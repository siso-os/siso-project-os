Agent Fleet Runtime Pack

A reusable project bootstrap for elastic, evidence-gated engineering teams with persistent Sol owners, bounded Luna workers, independent verifiers, isolated Git worktrees, durable callbacks, machine thresholds, and read-only Mission Control projections.

The pack adds no scheduler, task database, mail bus, daemon, merge queue, secrets store, or provider implementation.

Bootstrap and validate

project-os init . --name "My Project"
cp <package>/packs/fleet/fleet.bootstrap.example.json ./fleet.bootstrap.json
project-os fleet plan . --config fleet.bootstrap.json --json
project-os fleet init . --config fleet.bootstrap.json --json
project-os fleet check . --json
project-os check . --json

plan is read-only. init writes atomically only after the complete plan passes and refuses differing files. A same-host dead installer is resumed from matching managed bytes; incomplete temporary writes are removed and generated outputs are rebuilt under the recovered lock. Repeating the same install retains every matching byte. The base project-os init remains unchanged unless the optional fleet command is invoked.

Eligibility is not process start, completion, or qualification

Fleet admission is a single-use eligibility verdict. Process start belongs to the configured provider, which must atomically revalidate active claims, live assignments, verifier backlog, and machine thresholds while reserving the slot. Completion closes a canonical task or run. Qualification is an independent evidence verdict bound to the candidate SHA. None implies another.

project-os fleet admit . --file admission.json records admit, hold, or reject. For writes, admit requires an exact active work claim bound to task, actor, machine seat, base SHA, and write set. Path comparison is Unicode-normalized and case-insensitive so collisions fail closed across case-insensitive hosts; project control paths such as .agents, .project-os, .git, root loader files, and ledgers are reserved from fleet domains and candidates. The evaluator reads canonical task/domain/claim state and probes Git commits, repository cleanliness, evidence files, and checkpoint lineage directly; evidence must realpath beneath the task root and each reference must be a regular file. A verifier must name the canonical implementation owner or active claimant and remain independent of that actor. Callers cannot assert these facts with booleans. The evaluator also fails closed on missing, malformed, or incompatible Project OS versions; changed managed contracts; overlap; capacity or verifier pressure; stale recovery; unknown AC power when required; role-profile drift; self-verification; and repository/evidence escapes.

Admission receipts are created once under a lock and carry a digest over their canonical content. Checks detect later mutation, but the digest is tamper evidence rather than an identity signature or a provider slot reservation.

Crash, restart, and evidence recovery

  1. Provider identities use the configured durable field, normally terminal_id; pane and process IDs are explicitly volatile.
  2. Heartbeats older than policy are held until maintenance records a recovery disposition.
  3. A resumed candidate must own the canonical task and name a schema-valid immutable checkpoint created by that actor for that task.
  4. Abandoned assignments stop consuming projected capacity only after explicit disposition.
  5. Workers return candidate SHA, commands, artifacts, and observations; the Sol owner owns final claims.
  6. Verifier receipts remain separate from implementer write ownership and feed the existing run/delivery gates.
  7. Fleet installation uses atomic files, transactional rollback, and confirmed same-host dead-process lock recovery.
  8. Checks bind managed policy, process, repository, domain, role, source-contract, and task-template bytes to the installed pack before admission trusts them; mutable callbacks, admission receipts, and generated projections remain outside that managed digest set.

Elastic placement

Eligibility uses canonical active claims plus provider assignments and active missions, never a desired fleet size alone. Policy reserves ceil(max_live × verifier_ratio) or more slots for verifiers, limits pending verification, bounds each machine, and checks available disk, available memory, load per CPU, and AC power. Unknown AC state fails closed when power is required. A Mac Mini may host long-running worker/verifier lanes while a MacBook hosts lead, portfolio, or Front Door lanes; these are configured profiles, not hard-coded product assumptions.

Source-truth projection

TASK-GRAPH.json, TEAM-STATE.json, and FLEET.html are byte-deterministic read-only outputs. SOURCE-CONTRACT.json names every canonical input and forbids consumers from writing task, ownership, admission, completion, or qualification state through a projection. Normal project-os build and check include the fleet outputs only when the pack is installed.

Version and migration

The pack has its own semantic version in PACK.json and currently requires the installed Project OS version named in the manifest. Project OS 0.5.0 includes a checked-in 0.4.0 managed-file baseline, so upgrade plan can distinguish unchanged prior package files from project-authored edits. Plan the Project OS upgrade first, review managed-file collisions, then follow the fleet migration guidance in the target release. Never overwrite project-authored domain/policy records during an update; create a reviewed migration receipt and retain the old manifest until validation passes.

Actionist dog-food

npm run dogfood:fleet runs a public-safe, non-authoritative Actionist migration rehearsal in temporary parent and nested Git repositories. The published fixture retains only generalized capability and gap categories; its repository revision, actor identities, provider workspace, and repository locators are synthetic. It proves collision-free installation, direct temporary candidate-SHA/repository checks, an admitted independent verifier, a claim-bound conversion held behind incomplete dependencies and verifier backlog, deterministic projections, and full Project OS validation without mutating the live Actionist programme.
